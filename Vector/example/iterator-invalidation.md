# 迭代器失效

> 一句话结论：容器结构一变，之前保存的迭代器、指针、引用就全部作废——**重新取一次**。
>
> 具体到"边遍历边删除"：`erase(it)` 之后不能再 `++it`。**删了就用返回值，没删才前进。**

迭代器、指针、引用表达的都只是"此刻这块内存里的某个位置"，是门牌号，不是元素的身份证。一旦容器换了存储块，或者把元素搬了位置，这个地址就不再指代你当初记下的那个对象——标准把这种状态称为**失效**（invalidated）。对失效的迭代器做任何操作（解引用、自增、比较）都是未定义行为。

本文分三部分：第 1~3 章给规则（哪些操作让什么失效、失效分几类），第 4~11 章用一个真实案例把"结果对但代码错"讲透，第 12~14 章是其他场景与规避手法。后续实测数据均来自 `example/vector.h` 的 `XiYue::vector`。

同一段代码，只换数据，后果可以从"看起来正确"一路走到段错误：

```cpp
auto it = v.begin();
while (it != v.end())
{
    if (*it % 2 == 0)
    {
        v.erase(it);   // ① 让 it 作废
    }
    ++it;              // ② 又要求 it 可用
}
```

`①` 和 `②` 直接冲突。下面按"机制 → 后果 → 语言层面的规定"三层把它拆开。

## 1. 什么是迭代器失效

容器对外承诺"迭代器指向某个元素"。当内部发生变化，这个承诺就被撤回：

| 变化 | 后果 |
| --- | --- |
| 存储块被释放、另分配了一块 | 旧地址真的野了（换块失效） |
| 元素被整体搬移（前移、后移） | 地址还在容器内，但上面站着的是别的元素（搬家失效） |
| 元素个数变化 | `end()` 不再是原来的终点（尾后失效） |

三者的详细区别见第 3 章。这里先记住一条：**失效不等于地址一定变坏**。它只表示"这个地址不再承诺指向你要的元素"，所以你可能读到一个看似正常的数字，也可能直接段错误。

三种持有方式会一起失效，因为底子都是地址：

```cpp
auto it = v.begin() + 1;      // 迭代器
int* p  = v.begin() + 1;      // 指针
int& r  = v[1];               // 引用
```

本实现的迭代器就是裸指针（`typedef T* iterator;`），所以"迭代器失效"和"指针失效"在这里是同一件事；换成 `std::vector` 的调试迭代器，两者在**检测层面**才有差别（见第 14 章）。

失效之后只有三种结局，而且是随机给：

| 结局 | 典型场景 |
| --- | --- |
| 静默读错：不崩、不报错，结果错 | 搬家失效（`erase` 后继续用旧迭代器） |
| 写坏堆：很久之后在别处崩 | 换块失效（扩容后往旧地址写） |
| 立刻段错误 | 越界到不可访问的页（删尾后 `++it` 再 `erase`） |

## 2. 失效规则总表

| 操作 | 迭代器 / 指针 / 引用 | 说明 |
| --- | --- | --- |
| `push_back` | 扩容：全部失效<br>不扩容：仅 `end()` 变化 | 其余元素地址没动 |
| `pop_back` | 被弹出的那个位置失效，`end()` 后退 | 前面的元素不受影响 |
| `insert(pos, ...)` | 扩容：全部失效<br>不扩容：`pos` 及之后失效 | `pos` 之前仍有效 |
| `erase(first, last)` | `first` 及之后失效 | 前面的元素没被搬动 |
| `reserve(n)` | `n > capacity()` 时全部失效 | 否则什么都不做，也不失效 |
| `resize(n)` | 变大且扩容：全部<br>变大不扩容：仅 `end()`<br>变小：`[n, 旧 size)` 失效 | |
| `clear()` | 全部失效 | `size` 归零，`begin() == end()` |
| `swap(other)` | 仍指向原元素，但归属换成另一个容器 | 实用上当作失效，重新取 |
| `operator=` | 全部失效 | 旧块随形参析构被释放 |
| 析构 | 全部失效 | 存储块被 `delete[]` |

三条读表方法，能覆盖上表所有行：

1. **先问"换块了吗"**——重新分配就全废，没有例外。
2. **没换块再看"元素被搬动了吗"**——搬动范围（含起点）之后全废，之前仍有效。
3. **`end()` 永远跟着 `size()` 走**——`size` 一变，旧 `end()` 就不是终点，哪怕没换块。

本实现有一个容易误解的地方：`pop_back` / `erase` / `clear` / 缩小的 `resize` 都**不析构元素、不释放内存**，所以被"移出"的位置读出来还是原来的值。但那是残留数据，不是有效元素，读取仍属于 UB。

## 3. 三类失效

### 3.1 换块失效：旧地址真的野了

触发：`reserve`、扩容时的 `push_back` / `insert` / `resize`、`operator=`。

`reserve` 里先 `new T[n]`，再逐个赋值搬迁，最后 `delete[] _start`。从那之后旧地址就还给分配器了。实测：

```text
reserve 前  cap=4   begin=0x2752370
reserve 后  cap=64  begin=0x2752390   旧指针仍等于 begin? 0
旧指针读出的值 = 41231520             ← 已释放内存，UB
```

特点：地址变了；写入会破坏堆；用 ASan 之类的工具能抓到 use-after-free。

### 3.2 搬家失效：地址没变，人换了

触发：`erase`、不扩容的 `insert`（把元素整体前移或后移）。

实测 `{10, 20, 30, 40}` 删掉 20：

```text
erase 前  *it=20  地址=0xf22374
返回值    *ret=30 地址=0xf22374   与旧 it 同一地址? 1
容器现在是 10 30 40
```

`it` 和返回值是同一个地址，但那个位置上现在站着 30。你手里那个旧的 `it` 已经"作废"，只是它读出来恰好还是个正常数字。

特点：地址没变；不触碰非法内存；通常**不崩**，只是结果错。

### 3.3 尾后失效：没有非法内存，只是少了一格

触发：任何改变 `size()` 的操作。它甚至可以完全没有换块、没有搬家，只是 `end()` 挪了一格。

实测（`reserve(8)` 后放 3 个元素，再 `push_back` 第 4 个，容量够、不扩容）：

```text
扩容前 cap=8  旧 end 偏移=3
扩容后 cap=8  新 end 偏移=4
用旧 end 遍历得到 3 个元素（实际 size=4）
```

特点：全程合法内存，任何工具都抓不到，症状只是"少遍历了一个元素"。这是三类里最隐蔽的。

### 3.4 三者对照

| | 换块失效 | 搬家失效 | 尾后失效 |
| --- | --- | --- | --- |
| 地址是否改变 | 变了 | 没变 | `end()` 变了 |
| 旧内存是否已释放 | 是 | 否 | 否 |
| 访问是否触犯非法内存 | 是 | 否 | 否 |
| 典型症状 | 堆破坏、延迟崩溃 | 静默读错 | 少遍历一格 |
| 工具能不能抓 | ASan 能 | 调试迭代器能 | 基本抓不到 |

## 4. 机制：erase 替你前进了一次

循环里 `++it` 的含义是"当前元素检查完了，走到下一个"。而 `erase` 在删掉一个元素时，还会**把后面的元素整体向前挪一格**。挪完之后，"下一个"已经自己站到了 `it` 脚下。

```text
① 删之前          [1] [2] [3] [4] [5]
                       ↑ it            手指停在 2 上，准备删

② erase(2) 之后   [1] [3] [4] [5]
                       ↑ it            3 补位到脚下，it 一步没动

③ 再执行 ++it     [1] [3] [4] [5]
                           ↑ it        从 3 头上跨过去，落到 4
```

所以问题不是"地址无效了"，而是**进度走多了**：`erase` 已经替你前进了一次，你又前进了一次。

> 删了别动，没删才动。

## 5. 被跳过的永远是"紧邻的下一个"

因为 `erase` 只挪一格、`++it` 也只走一格，所以**被漏检的一定是刚被删掉的元素的紧邻下一个**：

```text
删 2 → 3 补位 → 漏检 3
删 4 → 5 补位 → 漏检 5
```

而这个"紧邻下一个"是什么，你的代码事先并不知道：

| 数据 | 删谁 | 顺带漏检谁 | 漏检的那个该不该删 | 结果 |
| --- | --- | --- | --- | --- |
| `1 2 3 4 5` | 2 | 3 | 不该（奇数） | 正确 |
| `1 2 3 4 5` | 4 | 5 | 不该（奇数） | 正确 |
| `1 2 4 5` | 2 | **4** | 该删 | 漏删 |
| `1 2 3 4 4 5` | 4 | **4** | 该删 | 漏删 |
| `1 2 3 4 4 5 4` | 4 | **4** | 该删 | 越界崩溃 |

### "跳过 3 有什么问题？"

单看这一件事：没问题。3 是奇数，跳过了本来就该留。

但要看清一点：**你的代码从来没有"跳过 3"这个意图。**

- 条件里只有一句 `if (*it % 2 == 0)`，说的是"偶数就删"，没有任何一句在说"可以跳过 3"。
- "跳过 3"是 `erase` 加 `++it` 组合出来的**副作用**，它和"跳过 4"是同一条语句的同一个副作用，只是撞上的数据不同。
- 跳过谁，完全由数据决定。`{1,2,3,4,5}` 的两次漏检恰好都撞上奇数，所以看不出来 —— 这是运气，不是正确性。

把这组数据改一个数字（3 换成 4），同一份代码立刻开始丢元素。用最简单的方式验证自己：

```cpp
std::vector<int> v{1, 2, 4, 5};     // 期望 [1 5]，实际 [1 4 5]
```

## 6. 结果对，不代表代码对

这是最容易漏掉的一层。同一组数据 `{1,2,3,4,5}`、同一份代码：

| 构建方式 | 运行结果 |
| --- | --- |
| g++ 默认（Release 语义） | 输出 `[1 3 5]`，完全正确 |
| g++ `-D_GLIBCXX_DEBUG` | 第 2 轮中止：`attempt to increment a singular iterator` |
| MSVC Debug | 第 2 轮中止：`vector iterator not incrementable` |

也就是说：**即使结果对，这行 `++it` 也是违规的**，只是没有检查层时没人拦你。

标准的规定在 `[vector.modifiers]`：`erase(pos)` 使 **pos 及其之后**的所有迭代器、指针、引用失效。这跟"跳过的是不是该删的元素"毫无关系。

调试版为什么能抓到？调试迭代器除了元素地址，还记着"我属于哪个容器"，容器则维护一份登记表（记录当前所有活着的迭代器）。`erase` 会沿登记表把落在删除点之后的迭代器全部摘掉；之后 `++it`、`*it`、甚至 `it != v.end()` 都会在校验时失败。Release 版把这段代码整段预处理掉了，迭代器退化成裸指针，`++it` 只是地址加一个元素长度。

## 7. 什么时候会真的崩

漏删还算温和，真正致命的是把迭代器推到 `end()` 之后。

### 7.1 删掉最后一个元素

数据 `{1, 2, 3, 4, 4, 5, 4}`，实跑记录：

```text
第1轮: 偏移=0 size=7 读到 1
第2轮: 偏移=1 size=7 读到 2
第3轮: 偏移=2 size=6 读到 4
第4轮: 偏移=3 size=5 读到 5
第5轮: 偏移=4 size=5 读到 4
第6轮: 偏移=5 size=4 读到 4      ← 偏移 5，size 只有 4
Segmentation fault
```

第 5 轮删掉的是最后一个元素：

```text
erase 前: [1] [3] [4] [5] [4]     it 在偏移 4
erase 后: [1] [3] [4] [5]         size 变成 4，偏移 4 就是 end()

代码仍执行 ++it → it 跑到偏移 5，即 end() 的后面一格

循环条件 it != v1.end() → 5 != 4 → 成立，继续进循环
```

接着：

1. `*it` 越界读偏移 5 的内存，读出来是 `4`；
2. `4` 是偶数，于是 `v1.erase(it)` 用一个越过尾部的迭代器去搬内存 → 段错误。

关键细节：**删掉最后一个元素时，`erase` 返回的就是 `end()`**。写成 `it = v.erase(it)`，循环条件立刻为假，自然结束；而错误的 `++it` 恰好把它推出了边界。

### 7.2 连续删除，每轮都多走一步

数据 `{2, 2, 2}`：

```text
第1轮: 偏移=0 size=3 读到 2
第2轮: 偏移=1 size=2 读到 2
第3轮: 偏移=2 size=1 读到 2      ← 已经是 end() 之后
Segmentation fault
```

### 7.3 为什么越界了还能读出数字

因为**缓冲区并没有释放**：`erase` 只减少 `size()`，`capacity` 不变，那块内存里还留着旧值。于是 `*it` 读到一个看起来"正常"的 `2` 或 `4`，程序继续往下跑，真正的破坏发生在后面那次 `erase` 上。

这也是 UB 最难查的地方：出错的位置和崩溃的位置不在一起。

## 8. 两种迭代器失效，别混为一谈

迭代器失效不是一种现象。按"内存有没有被释放"来分，至少有两类，后果和处理方式完全不同。第 3 章按表现分了三类，这里把它们放回这个案例里对照一次：

| 类型 | 触发 | 内存状态 | 不检查的后果 |
| --- | --- | --- | --- |
| 换块失效 | `push_back` / `insert` 扩容 | 旧块被 `delete[]`，指针真的野了 | 写已释放内存，堆破坏，可能很久之后才崩 |
| 搬家失效 | `erase`、中间 `insert` | 内存还在，地址甚至仍在容器内 | 完全静默：读到别的元素，结果错，通常不崩 |

`erase` 属于第二种：地址没变，但这一格上装的对象换了身份。标准因此宣布迭代器失效——不是因为指针坏了，而是因为**它不再指代刚才那个元素了**。

## 9. 正确写法

### 9.1 逐个删除：两条分支互斥

```cpp
auto it = v.begin();
while (it != v.end())
{
    if (*it % 2 == 0)
    {
        it = v.erase(it);   // 删了：接住返回值，绝不 ++
    }
    else
    {
        ++it;               // 没删：正常前进
    }
}
```

`erase` 的返回值就是"补位后站在这一格上的元素"的位置。它和你原来的 `it` 指向同一格，但它是重新登记过的、可以继续用。

补一句复杂度：这种写法是 O(n²)，每删一个都要搬一次后面的元素。

### 9.2 批量删除：交给算法

```cpp
// C++20
std::erase_if(v, [](int x) { return x % 2 == 0; });

// C++20 之前
v.erase(std::remove_if(v.begin(), v.end(),
                       [](int x) { return x % 2 == 0; }),
        v.end());
```

一次线性整理 + 截断尾部，O(n)，而且全程不持有会失效的迭代器。

## 10. 自测

1. `{2, 2, 2}` 用错误写法会发生什么？
2. 为什么 `it = erase(it)` 之后**不能**再 `++it`？
3. 删到最后一个元素时，`erase` 的返回值是什么？
4. 为什么 Release 下这段代码"从来不崩"？
5. 想用一组数据同时验证"漏删"和"越界"，应该怎么造？
6. 为什么 `{1,2,3,4,5}` 的结果是对的，代码仍然是错的？

参考答案：

1. 崩溃。每轮都删、每轮都 `++`，第三轮 `it` 已在 `end()` 之外，读到缓冲区残留的 `2`，随后 `erase` 越界搬运触发段错误。
2. 返回值已经指向下一个待检查的元素，再 `++` 就跳过一个。
3. 新的 `end()`。
4. 没有检查层（`_ITERATOR_DEBUG_LEVEL=0`），`++it` 就是地址加一个元素长度，不报错也不一定崩。
5. 末尾放一个待删元素，例如 `{1,2,3,4,4,5,4}`：中间漏删一个 4，最后越界崩溃。
6. 两次漏检都恰好撞上奇数（3 和 5），被跳过的元素本来就不该删。代码并没有"判断"过这一点，是数据凑巧；换成 `{1,2,4,5}` 就会丢元素。

## 11. 检查清单

写任何"边遍历边删除"的循环前过一遍：

- [ ] 循环体里是否修改了容器结构？
- [ ] 修改之后，有没有再动旧迭代器（`++`、`*`、比较都算动）？
- [ ] 删除后用的是 `erase` 的返回值，还是原来那个迭代器？
- [ ] 测试数据里有没有**相邻的待删元素**（如 `4 4`）？
- [ ] 测试数据里有没有**位于尾部的待删元素**？
- [ ] 数据量稍大时，这个循环会不会退化成 O(n²)？要不要改用 `erase_if`？

## 12. 其他场景：push_back 与 insert

`erase` 只是最容易踩的一个。另外两个高频场景同样会失效，而且都不带任何提示。

### 12.1 push_back 扩容后继续用旧指针

```cpp
XiYue::vector<int> v;
v.reserve(2);
v.push_back(1);
v.push_back(2);
int* p = v.begin();      // 记下首地址

v.push_back(3);          // size 到 3，超过容量 2 → 扩容，旧块被 delete[]
std::cout << p[0];       // 读已释放内存
```

实测：

```text
push 前 cap=2  p=0xee2370
push 后 cap=4  begin=0xee2390   旧 p 仍等于 begin? 0
旧 p[0] = 15606704              ← 旧块已释放，读到的是垃圾
```

这属于换块失效。"容量够就不会失效"这句话只对**其他元素的位置**成立，`end()` 照样会变（尾后失效）。

### 12.2 insert 之后继续用插入点或它后面的迭代器

```cpp
XiYue::vector<int> v{1, 2, 3};
auto it = v.begin() + 1;   // 指向 2

v.insert(v.begin(), 0);    // size 3 == cap 3 → 扩容
std::cout << *it;          // 地址已释放
```

实测：

```text
insert 前 *it=2  cap=3
insert 后 容器 = 0 1 2 3  cap=6
旧 it 读出的值 = 0        ← 地址已释放，不代表 2
```

标准规定 `insert` 使插入点及之后的迭代器全部失效；扩容时则是全部失效（包括插入点之前的）。`insert` 的返回值指向新插入的元素，是唯一可靠的锚点。

### 12.3 对照：用下标就没事

```cpp
XiYue::vector<int> v{1, 2, 3};
for (std::size_t i = 0; i < v.size(); ++i)
{
    v[i] *= 10;            // 每轮重新用 v[i]，不保存任何位置
}
```

```text
10 20 30
```

下标是相对量，只要还在 `[0, size())` 内就永远指向"第 i 个元素"，容器怎么扩容都不影响它。

## 13. 安全持有位置的三种方式

| 方式 | 写法 | 适合 |
| --- | --- | --- |
| 存下标 | `size_t i = ...;` 之后一律 `v[i]` | 跨越多次修改仍要定位同一个元素 |
| 接住返回值 | `it = v.erase(it);`、`it = v.insert(it, x);` | 遍历中修改，需要知道"下一个在哪" |
| 用完就重新取 | 每次修改后 `v.begin()` / `v.end()` | 一次性遍历，或整段逻辑不跨修改 |

再加上一条铁律：

> 只要两条语句之间可能发生"改变容器结构"的操作，就不要跨越它保存位置。
> 真要跨，就保存**值**或**下标**，不要保存**位置**。

判断"会不会改变结构"很简单——看这个操作有没有可能扩容或搬动元素：`push_back` / `insert` / `erase` / `reserve` / `resize` / `clear` / `operator=` 都算，`operator[]`、`size()`、`capacity()`、`empty()` 不算。

## 14. 怎么让错误尽早暴露

| 手段 | 能抓什么 | 抓不到什么 |
| --- | --- | --- |
| `-D_GLIBCXX_DEBUG`（`std::vector`） | 对已失效迭代器做 `++` / `*` / 比较 | 尾后失效；对本实现完全无效 |
| MSVC Debug（`_ITERATOR_DEBUG_LEVEL=2`） | 同上，消息为 `vector iterator not incrementable` | 同上 |
| ASan / valgrind | 换块失效（use-after-free） | 搬家失效、尾后失效 |
| 本实现的 `assert` | 下标越界 | 任何形式的失效 |
| 纪律 + 第 11 章清单 | 三类都能避开 | 不是自动的，靠人 |

为什么本实现里调试库那一套用不上：`iterator` 就是 `T*`，没有"我属于哪个容器"的登记信息，`erase` 无从知道你手里还握着哪些指针。标准库的调试迭代器是包装类，才能做到"点名作废"。

也正因为如此，**搬家失效和尾后失效几乎只能靠规则避免**——它们访问的都是合法内存，工具没有理由报警。
